# Design

## Context

См. `proposal.md` — Why. Технические обстоятельства, которые определяют подход:

- Оформление уже централизовано: `src/styles/tokens.css` держит блок `@theme` и выпускает те же значения в
  `:root`; Tailwind строит утилиты из этих токенов. Слои разделены верно, поэтому смена палитры — это
  правка одного файла, а не поиск цветов по разметке.
- Движение сегодня: `transition` только для `border-color/background-color/color` в базовом слое
  (`app.css`), `animate-pulse` у скелетонов и точек набора в `MessageThread`, один `transition-opacity` на
  действиях строки в `GuidelineRow`. То есть шкалы движения нет, но и «сопротивления» ей нет.
- Глушитель `@media (prefers-reduced-motion: reduce)` уже глобальный: любое новое CSS-движение покрывается
  им автоматически, если не появляется JS-driven анимаций.
- Шрифты приходят из `scripts/fetch-fonts.mjs`: он тянет CSS Google Fonts, оставляет только subsets
  `latin`, `cyrillic`, `cyrillic-ext` и удаляет неиспользованные файлы. Добавление семейства — это одна
  строка в `FAMILIES` плюс перегенерация `styles/fonts.css`.
- Тесты в основном серверные (серверный рендер через `node`) и читают текст и ссылки; DOM-тесты
  (`jsdom` + `@testing-library/react`) есть только у оверлеев — `Dialog`, `Combobox`, `Toast`, `Field`.
  Поэтому разметка ломает часть тестов, а поведение — почти нет.
- В зависимостях есть `@radix-ui/react-dialog`, `popover`, `toast`, `tooltip`. `dropdown-menu` нет —
  меню темы собирается на `popover`, новых пакетов изменение не требует.
- `vite`/`vitest` при запуске выполняют `exec("net use")` и в песочнице падают с `spawn EPERM`; сборка,
  тесты и выгрузка шрифтов требуют полного доступа к системе.

## Goals / Non-Goals

**Goals:**

- Двухрежимная палитра, где тёмная — первичная: значения выводятся для тёмной темы и подгоняются под неё,
  а не инвертируются из светлой.
- Один визуальный язык на все экраны: каркас, типографика, движение и бренд описаны один раз и не
  повторяются в экранах.
- Сохранить архитектурное разделение: компоненты презентационные, логика в `store/`, `hooks/`, `lib/`,
  `api/`. Ни один файл этих каталогов не меняется.
- Сохранить инварианты: контраст AA в каждой теме, `prefers-reduced-motion`, статус не кодируется только
  цветом, вердикт без `chunk_id` не выдаётся.

**Non-Goals:**

- Библиотека анимаций (`framer-motion`, `motion`): выигрыш в ощущениях не оправдывает вес и ломку тестов.
- View Transitions API: поддержка в браузерах неровная, а переходы между экранами решаются fade+rise.
- Палитра команд `⌘K`: требует нового взаимодействия и собственных тестов; из шапки её кнопка не
  рисуется, чтобы не обещать несуществующее.
- Плотность списка (переключатель «список/сетка»): это новая настройка с сохранением, то есть логика.
  Строки библиотеки просто оформляются как карточки.
- Мобильная вёрстка ниже 1024px, экран вердикта, серверный поиск по названию.

## Decisions

### D1. Тёмная тема первична, светлая выводится

Токены объявляются дважды — под `[data-theme='dark']` и `[data-theme='light']` — с общим смысловым
набором имён. Светлая палитра получает значения, подобранные под тёмную (одинаковая иерархия
поверхностей, тот же жар акцента), а не полученные инверсией.

Почему: инверсия даёт либо «серую кашу», либо статусы, которые в тёмной теме кричат. Роли должны
сохраняться в каждой теме независимо, а это значит, что обе таблицы значений — ручная работа.

Альтернативы:

| Вариант | Причина отказа |
|---|---|
| Только светлая + акцент поярче | не решает главного: PDF-страница на тёмном фоне читается лучше, а это основной режим |
| Только тёмная | днём и в светлом помещении светлая половина нужна; продукт клинический |
| `prefers-color-scheme` без переключателя | пользователь не может уйти от системной настройки — типичная претензия к «умным» темам |
| `light-dark()` в CSS | короче, но требует `color-scheme` на каждом узле и не даёт переключателя без дублирования |

### D2. Значения палитры и проверенный контраст

Считал относительную яркость по sRGB. Ключевые пары:

| Пара | Тёмная | Светлая |
|---|---|---|
| ink `/` bg | `#e8eefb` на `#0b1220` — 16.1:1 | `#0b1220` на `#f6f8fb` — 17.6:1 |
| muted `/` bg | `#94a3b8` на `#0b1220` — 7.3:1 | `#475569` на `#f6f8fb` — 7.1:1 |
| faint `/` bg | `#7c8aa3` — 5.4:1 | `#52627a` — 5.8:1 |
| accent `/` bg | `#22d3ee` на `#0b1220` — 10.4:1 | `#0f766e` на `#ffffff` — 5.5:1 |
| текст на accent-заливке | `#04222c` на `#22d3ee` — 9.1:1 | `#ffffff` на `#0f766e` — 5.5:1 |
| mark `/` surface | `#fcd34d` на `#111a2e` — 12.0:1 | `#fcd34d` на `#ffffff` — 1.4:1 (только заливка, не текст) |

Два вывода, которые нельзя разойтись с кодом:

- Прежний `--color-text-faint` `#64748b` в тёмной теме даёт **3.9:1** — то есть второстепенный текст
  нарушил бы требование. Поэтому faint — отдельное значение на тему, а не общий серый.
- Акцент в тёмной теме не переносится в светлую и наоборот: `#22d3ee` на белом даёт **1.8:1**. Две
  независимые акцентные рампы — обязательное следствие, а не удобство.

Второй акцент (фиолетовый) существует только для градиента и декора:
`#8b5cf6` на тёмном фоне даёт **4.4:1** и как текст непригоден, поэтому текстовый вариант — `#a78bfa`
(6.9:1); в светлой теме `#7c3aed` проходит как текст (5.7:1).

Статусы клинрека задаются **непрозрачными** парами «фон + текст + рамка» на каждую тему. Полупрозрачная
заливка («accent 12% поверх поверхности») делает итоговый контраст зависящим от подложки, посчитать его
заранее нельзя, а спека требует вычислимого контраста.

### D3. Тема без мигания и без новой логики

Порядок применения: инлайн-скрипт в `<head>` до первой отрисовки читает сохранённый выбор из
`localStorage` и ставит `data-theme` на `<html>`; React дальше только синхронизирует переключатель.
Скрипт — несколько строк в `index.html`, не в `src/`.

Почему так: если тему ставит React после монтирования, на тёмной системе пользователь видит вспышку белого
экрана. Это единственная причина, по которой тема не может быть «просто классом на `#root`».

`color-scheme` меняется вместе с `data-theme` (нативные скроллбары и контролы), `theme-color` обновляется
из того же хука — двух мета-тегов через `media` недостаточно, потому что ручной выбор сильнее системного.

Состояние темы живёт в `components/ui/ThemeToggle` + хук рядом с ним. В `store/` ничего не добавляется.

### D4. Unbounded только в display-роли, два веса

`FAMILIES` получает `{ family: 'Unbounded', slug: 'unbounded', query: 'Unbounded:wght@400;600' }` — два
веса × три подмножества = шесть файлов. Кириллица подтверждена по метаданным Google Fonts (`coverage`
содержит `cyrillic`, язык `ru_Cyrl`), лицензия OFL.

Правила применения — часть дизайн-системы, а не вкусовщина:

- 400 — display и заголовки экранов, 600 — только wordmark.
- Трекинг отрицательный (`-0.02…-0.03em`), межстрочный 1.08 для display и 1.15 для h1: метрики семейства
  высокие, дефолтный `1.24` для крупного кегля рыхлый.
- К body и цитатам неприменим: семейство широкое, строка теряет треть символов на той же ширине.
- Числа остаются `JetBrains Mono`: спека требует выровненных разрядов в таблицах и счётчиках, а у
  Unbounded своя цифровая система.

Альтернативы: Onest/Golos Text (нейтрально, без характера), Bricolage Grotesque (отклонён: **нет
кириллицы**), Literata/Playfair (возврат к засечкам, отклонённым на прошлом ревью).

### D5. Бренд-знак: скобки-чанк

Знак — две скобки с точкой/пульсом внутри: это буквальная форма инварианта «вердикт указывает на
конкретный чанк». Реализуется как `components/ui/Logo.tsx` с `currentColor`, два варианта (`mark`,
`mark + wordmark`), чтобы знак жил на токенах и работал в обеих темах без отдельных ассетов.

Почему не монограмма и не «пульс в квадрате»: монограмма нейтральна и не отличает продукт, кардиограмма
в 16px превращается в мусор (после сжатия остаётся одна линия).

Favicon: `favicon.svg` + `favicon.ico` + `apple-touch-icon`; в 16px у знака проверяется читаемость на
светлой и тёмной панели вкладок — если проваливается, у favicon-варианта появляется подложка из токена
surface.

Название «Smart Doctor» сохраняется. Идентификаторы (`smart-doctor-backend`, `smart_doctor` в compose,
`uuid5(..., "smart-doctor/guideline-chunk")` в `chunking.py`) не затрагиваются: `chunk_id` выводится из
последней строки, и её изменение сломало бы привязку вердиктов к чанкам.

### D6. Каркас: топбар + сегментированная навигация

```
+----------------------------------------------------------------+
| [SD] Smart Doctor                                 [ тема ]     |  56px, sticky + glass
+----------------------------------------------------------------+
|   ( Библиотека  |  Новый протокол  |  Чат )                    |  44px, сегменты
+----------------------------------------------------------------+
```

- Сегменты — навигация, а не табы: `NavLink` + `aria-current="page"`, без `role="tablist"`. Табы
  семантически обещают переключение панелей, которого нет.
- Стекло постоянно (sticky + `backdrop-filter` + бордер), без листенера прокрутки: нет нового
  UI-состояния, нет дребезга.
- Просмотрщик PDF на весь экран: у layout появляется вариант без общей рамки. Реализация — вариант
  компонента оболочки на уровне маршрута, данные и хуки не меняются.
- `⌘K` не рисуется: обещание палитры без палитры хуже отсутствия кнопки.

### D7. Шкала движения

```css
--motion-fast: 120ms;   /* hover, нажатие, цвет */
--motion-base: 180ms;   /* появление оверлеев, строк */
--motion-slow: 280ms;   /* смена экрана, вспышка цитаты */
--ease-out: cubic-bezier(0.2, 0.8, 0.2, 1);
--ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1); /* только появление и нажатие */
```

Разрешённые места: смена экрана (fade + 4px), появление строк списка (stagger 30ms, не больше 8 строк,
только первая отрисовка, не фильтрация), появление диалога/тоста/комбобокса (spring), вспышка подсветки
при переходе к цитате (280ms), нажатие кнопки (`active:scale-[0.98]`).

Запрещено: анимация canvas PDF, задержка действия окончанием анимации, движение, которое несёт
единственную информацию о смене состояния, а также `animate-pulse` мимо шкалы — существующие скелетоны и
точки набора переводятся на общие токены в этой же работе.

### D8. Статусы, фокус и подсказки в тёмной теме

- Статусы: непрозрачные пары на тему, цвет всегда сопровождается текстом (требование спеки, не новое).
- Фокус: кольцо акцента с отступом; на акцентной заливке кольцо инвертируется (внутренний контраст), иначе
  на primary-кнопке оно не видно.
- Цитата источника: остаётся левая линейка маркера и больший кегль, чтобы в тёмной теме не смешаться с
  текстом интерфейса.
- Маркер подсветки чанка живёт на белой PDF-странице и не меняется между темами; тёмная тема меняет только
  окружение страницы.

### D9. Никаких новых зависимостей

Меню темы — на `@radix-ui/react-popover` (уже установлен, даёт фокус-трап и клавиатуру). Движение — CSS.
Иконки — `lucide-react`. Бандл не растёт, тестовая инфраструктура не меняется.

### D10. Порядок работ и откат

Восемь шагов из `tasks.md`, каждый заканчивается работающим приложением: токены и шрифты → каркас и
бренд → библиотека → просмотрщик → форма → чат → полировка. Откат на любом шаге — возврат файлов одного
экрана; после последнего шага — `git revert` изменения целиком.

## Risks / Trade-offs

- **Две акцентные рампы удваивают поверхность визуальных проверок** → таблица посчитанных пар в D2,
  контраст проверяется в задаче каждого шага, а не один раз в конце.
- **Стекло и градиент делают контраст зависящим от подложки** → текст никогда не лежит на градиенте;
  градиент — декоративный слой под поверхностью, стекло применяется только к шапке поверх сплошного фона.
- **Unbounded широкий** → только display-роль, размеры ограничены `clamp`, трекинг отрицательный,
  wordmark фиксируется на 15–17px; проверка на самом длинном заголовке экрана.
- **Вспышка темы при загрузке** → инлайн-скрипт в `<head>` до отрисовки; проверка — перезагрузка на
  тёмной системе при сохранённой светлой теме.
- **Разметка ломает тесты** → тесты, читающие структуру, обновляются в той же задаче, где меняется
  компонент; поведенческие тесты (статусы, адреса, ошибки) остаются как есть.
- **`vite`/`vitest` в песочнице требуют полного доступа** (`spawn EPERM`) → сборка, тесты и выгрузка
  шрифтов выполняются в режиме с полным доступом; `--cache .tmp-npm-cache` при установке.
- **Соблазн «улучшить» тексты статусов при редизайне** → спека прямо запрещает менять смысл; тесты на
  подписи статусов остаются красной линией.
- **Правка может зацепить логику** → в каждой задаче просматриваются изменённые пути: `src/store/`,
  `src/hooks/`, `src/lib/`, `src/api/` и `backend/` в диффе быть не должно.

## Migration Plan

1. Токены v3 (две темы), шрифты, базовый слой; старые экраны продолжают работать на новых токенах.
2. Инлайн-скрипт темы, `color-scheme`, `theme-color`, `ThemeToggle`, `Logo`, favicon, `og:image`, каркас
   G3. После этого шага приложение выглядит новым, экраны — ещё нет.
3. Библиотека: карточки, stagger, фильтры-чипы, состояния без данных.
4. Просмотрщик: тёмное окружение, стеклянный тулбар, вспышка цитаты, вариант лейаута на весь экран.
5. Форма протокола: секции-карточки, закреплённое действие, ошибки рядом с полем.
6. Чат и состояния без данных (пустая библиотека, пустой чат, NotFound).
7. Полировка: контраст обеих тем, фокус на цветных поверхностях, `prefers-reduced-motion`, обновление
   `AGENTS.md` и `frontend/README.md`.

## Open Questions

- Точные hex статусных пар в светлой теме (там прежние значения остаются рабочими, тёмные подбираются по
  критерию «текст ≥4.5:1 на своей заливке, рамка ≥3:1») — фиксируются в задаче 1, спека от этого не
  зависит.
- Нужен ли `og:image` статическим файлом или генерируемым на сборке — пока статический, это не влияет ни
  на требования, ни на порядок работ.

## Проверка контраста (шаг 7.1)

Значения посчитаны по факту, а не по замыслу: пары берутся прямо из `tokens.css`, коэффициент считается
по WCAG для sRGB. Пройдены все 44 пары — текст не ниже 4.5:1, границы полей не ниже 3:1. Рамки
статусных плашек идут с порогом 1:1 осознанно: это декор внутри метки, а статус всегда подписан текстом.

Проверка нашла реальную ошибку: тон `mark` брал `ink`, и в тёмной теме текст на жёлтом маркере давал
**1.24:1**. Поэтому появился отдельный токен `--t-mark-ink` — маркер не меняется между темами, значит и
текст на нём всегда тёмный; стало 12.98:1 в обеих темах.
