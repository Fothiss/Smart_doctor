# Design

## Context

Мотивация — в [proposal.md](proposal.md), требования — в [spec.md](specs/guideline-chat/spec.md).

Состояние кода, которое определяет решения:

- Чанк уже несёт всё для цитаты (`chunk_id`, `guideline_id`, `guideline_version`, `section`, `page`, `bbox`, `rects`) и
  целиком лежит payload'ом в Qdrant — поиск с `with_payload` отдаёт текст и геометрию без второго запроса.
- В `ChunkVectorStore` есть только `upsert/get/delete`; `Embedder.encode_query` написан и нигде не вызывается.
- Инструкция запроса `EMBEDDING_QUERY_INSTRUCTION` сформулирована под протокольные утверждения («clinical protocol
  statement»), а не под вопросы.
- Просмотрщик открывает `?chunk=<id>` и подсвечивает прямоугольники — переход из ответа реализуется ссылкой, без правок.
- LLM-клиента нет; `LLMSettings` объявляет провайдера и ключи.
- Слои: `routers` → `services` → `clients`; промпты и схемы structured output — только в `app/services/prompts/`.

## Goals / Non-Goals

**Goals**

- Один HTTP-вызов на реплику: вопрос → ответ со ссылками; без серверного состояния.
- Цитаты проверяемы кодом: ссылка живёт только если её цитата дословно есть в чанке.
- Поиск ограничен выбранными документами на уровне запроса к хранилищу, а не промпта.
- Слой LLM изолирован в `clients`, чтобы смена провайдера не трогала сервисы.

**Non-Goals**

- Агент с тулзами, повторный поиск по инициативе модели.
- Reranker, гибридный (BM25) поиск, соседние чанки.
- Стриминг ответа, хранение ленты, оценка качества (golden set).
- Изменения в просмотрщике, библиотеке, ingestion и спеке формы протокола.

## Decisions

### 1. Клиент LLM на `langchain-gigachat` + `with_structured_output`

`GigaChat(credentials=…)` из `langchain_gigachat`; `credentials` — ключ авторизации из `GIGACHAT_TOKEN`, OAuth-токен
SDK получает и продлевает сам. Вызов — `llm.with_structured_output(Schema, include_raw=True)` и `ainvoke`.

Почему: structured output и LangChain-сообщения из коробки; `include_raw` даёт `parsing_error` и `usage_metadata`, то
есть провал разбора и расход токенов не теряются; `ainvoke` нативно асинхронный.

Альтернативы: официальный SDK `gigachat` напрямую (`achat.parse`) — меньше зависимостей, но тогда LangChain-слой
появится всё равно при первом же агенте; свой HTTP-клиент — полностью отвергнут (свой OAuth и свой разбор).

`method="function_calling"` по умолчанию; `method="json_schema"` (нативный `response_format`) — beta, включается
переменной `GIGACHAT_STRUCTURED_METHOD` после проверки на реальных ответах.

Клиент создаётся лениво в `Runtime` (по образцу `embedder`), как `LLMClient(Protocol)` — в тестах подменяется фейком.

### 2. Два последовательных structured-вызова, не один

`rewrite` (`SearchQuery`) → поиск → `answer` (`LlmAnswer`). Один вызов не решает эллипсис: поисковый запрос нужно
построить **до** поиска.

Альтернативы: склейка строк без LLM — дешевле, но не разворачивает эллипсис; агент с тулзой `search` — отклонён:
инвариант цитирования сложнее проверять, латентность и стоимость растут, поведение перестаёт быть воспроизводимым.

### 3. Поисковый запрос — тезис в регистре протокола, а не вопрос

`SearchQuery.expression` — самодостаточная фраза 5–20 слов с сохранёнными условиями (возраст, заболевание, степень,
препарат). Регистр совпадает с `EMBEDDING_QUERY_INSTRUCTION`, поэтому чат и будущая проверка протокола используют один
retrieval-путь и одну инструкцию. Телеграфный набор слов отвергнут: теряет связи между предметом и условиями.

### 4. Rewrite всегда; надёжность — проверкой результата, не гейтом

Гейт по длине и маркерам отсылки отклонён: он экономит вызов, но пропускает настоящие уточнения и требует тюнинга без
данных. Вместо него три слоя на выходе `rewrite`:

1. промпт требует вернуть самодостаточный вопрос без добавленных условий;
2. `SearchQuery.constraints` — список условий, которые обязаны остаться; код проверяет вхождение каждого;
3. при пустом, слишком коротком результате или потере условия — детерминированный откат на `предыдущий вопрос + текущий`.

Проверка входит в `ChatService`/`QueryRewriter`, а не в сервис LLM: это доменное правило, а не транспорт.

### 5. Окно истории — 4 сообщения

Клиент присылает ленту, сервер обрезает до `CHAT_HISTORY_WINDOW = 4`. В промпт ответа история **не** попадает: только
поисковый запрос и текущий вопрос, иначе модель начинает опираться на прошлые ответы вместо фрагментов.

### 6. Ссылки внутри ответа — по номерам

Контекст нумеруется `[1]…[K]`; модель возвращает `citations[{n, quote}]`, сервер сопоставляет `n → chunk_id`. UUID в
выводе модели не появляется: 36 символов она искажает, а сверка номера дешёвая.

### 7. Сверка цитаты — после нормализации

Текст чанка и цитата сравниваются после приведения: нижний регистр, `ё → е`, любые тире → `-`, схлопнутые пробелы,
удалённые кавычки-ёлочки. Дополнительно цитата короче `MIN_QUOTE_CHARS = 10` считается неподтверждённой: совпадение
из трёх слов ничего не доказывает.

### 8. Отказ — состояние ответа, а не ошибка

`status: "answered" | "not_found"`. Отказ возвращается `200` с пустыми `citations`, поэтому интерфейс отличает «в
документах нет» от сбоя и не показывает текст модели без ссылок. Ошибки внешних систем — только `502`/`503`.

### 9. Поиск одним запросом к Qdrant

`query_points(query=vector, query_filter=Filter(must=[MatchAny(guideline_id)]), limit=top_k, with_payload=True)`.
Фильтр — жёсткое условие «только выбранные документы». Порог `CHAT_MIN_SCORE` объявлен, но по умолчанию `0`
(отключён): масштаб косинусных оценок этого эмбеддера не измерен, включать порог вслепую — значит терять ответы.

### 10. Ответ модели выводится как markdown

GigaChat отвечает списками, выделениями и таблицами; в plain text они схлопываются в сплошную строку. Рендер идёт
через `react-markdown` + `remark-gfm` с компонентами на токенах проекта.

Маркеры `[n]` перед рендером превращаются в обычные markdown-ссылки `[n](#cite-n)`, а компонент ссылки разбирает
`href`: `#cite-n` → переход на фрагмент, путь приложения → `Link`, всё остальное — текст. Так разметка внутри пунктов
и таблиц не ломает маркеры, а внешние адреса, которые модель может придумать, не становятся переходами.

Модель нумерует фрагменты всего контекста (до восьми), а ссылается на два-три, поэтому её номера в ответе дают дыры
вида «[4] и [5]». При показе номера пересчитываются подряд по порядку появления ссылок, а адресом остаётся номер
фрагмента в контексте. Групповой маркер `[3, 5]` разбирается на отдельные ссылки; неподтверждённые номера из группы
убирает сервер.

Альтернативы: собственный разбор подмножества markdown — дешевле по зависимостям, но неполон (таблицы, вложенные
списки); `dangerouslySetInnerHTML` — отвергнут: HTML от модели выполнялся бы в приложении врача.

### 11. Лента чата живёт в памяти приложения

Сервер по-прежнему stateless. Состояние ленты и черновика вопроса поднято выше маршрутов (`ChatSessionProvider` вокруг
`Routes`): экран чата размонтируется при уходе в библиотеку, а сессия остаётся, поэтому разговор не теряется. Полная
перезагрузка страницы создаёт новое приложение и новую сессию — лента начинается с нуля. Кнопка «Новый чат» чистит и
ленту, и черновик.

Альтернативы: `sessionStorage` — переживает и перезагрузку, что противоречит требованию «после F5 чат пуст»;
`localStorage` — оставляет медицинский текст на диске; серверные сессии — новый контракт и хранение текста вопросов.

## API-контракт

`POST /api/chat/ask`

```json
{
  "guideline_ids": ["7434ecc7-58ec-4925-9b93-cb4d507646ca"],
  "question": "А если ещё и диабет, до какого давления снижать?",
  "history": [
    { "role": "user", "text": "До какого давления снижать пациенту 60 лет?" },
    { "role": "assistant", "text": "… [1]", "citations": [{ "chunk_id": "…" }] }
  ]
}
```

```json
{
  "status": "answered",
  "answer": "Снижать до <140/90 мм рт. ст. [1]; при диабете — до 130/80 [2].",
  "citations": [
    {
      "n": 1,
      "chunk_id": "4f1d…",
      "guideline_id": "7434ecc7-…",
      "guideline_version": 1,
      "guideline_title": "Гипертензия",
      "section": "3.2",
      "page": 9,
      "quote": "Целевой уровень АД — ниже 140/90 мм рт. ст."
    }
  ],
  "search": { "expression": "целевой уровень АД у пациента 60 лет с диабетом", "rewritten": true, "constraints_lost": 0 },
  "searched_guidelines": [{ "guideline_id": "7434ecc7-…", "title": "Гипертензия", "version": 1 }]
}
```

`not_found`: `answer: null`, `citations: []`, `search` и `searched_guidelines` заполнены.

| Ситуация | Ответ |
|---|---|
| пустой вопрос, нет документов, больше `CHAT_MAX_GUIDELINES` документов | `400` |
| неизвестный `guideline_id` | `404` |
| выбранный документ не `ready` | `409` |
| векторное хранилище недоступно | `503` |
| LLM: ошибка, таймаут, ответ не по схеме | `502` |

## Поток

```
question + window(4) + guideline_ids
   │ проверка документов (существуют, ready, версии фиксируются)
   ▼
QueryRewriter ── LLM #1 (SearchQuery) ── сверка constraints ── откат при провале
   │ expression
   ▼
RetrievalService: encode_query → Qdrant filter(guideline_ids) → top_k → бюджет контекста
   │ K чанков
   ▼
ChatService: рендер контекста [1]..[K] → LLM #2 (LlmAnswer) → сверка n и quote → status
   ▼
ChatAnswer
```

## Конфигурация

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GIGACHAT_TOKEN` | — (обязательна для чата) | ключ авторизации, передаётся как `credentials` |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` | scope API |
| `GIGACHAT_MODEL` | `GigaChat-3-Ultra` | модель ответа |
| `GIGACHAT_REWRITE_MODEL` | `GigaChat-2` | модель переписывания: дешевле и быстрее |
| `GIGACHAT_BASE_URL` | `https://api.giga.chat/v1` | адрес API |
| `GIGACHAT_VERIFY_SSL_CERTS` | `false` | локально без сертификата Минцифры |
| `GIGACHAT_CA_BUNDLE_FILE` | — | путь к CA, включает проверку в проде |
| `GIGACHAT_STRUCTURED_METHOD` | `function_calling` | `json_schema` — когда beta проверена |
| `GIGACHAT_TIMEOUT` | `60` | таймаут запроса, с |
| `GIGACHAT_MAX_RETRIES` | `3` | ретраи 429/5xx внутри SDK |
| `CHAT_TOP_K` | `8` | сколько фрагментов попадает в контекст |
| `CHAT_MAX_CONTEXT_CHARS` | `12000` | бюджет контекста, лишние фрагменты отбрасываются |
| `CHAT_MAX_GUIDELINES` | `5` | предел выбранных документов |
| `CHAT_HISTORY_WINDOW` | `4` | окно сообщений для переписывания |

`GIGACHAT_TOKEN` объявляется `SecretStr`; `.env.example` правится в том же изменении, иначе `test_settings.py` поймает
расхождение.

## Risks / Trade-offs

- **[Промах retrieval] нужный фрагмент не попал в топ-8 → честный отказ вместо ответа** → `CHAT_TOP_K=8` (модели дешевле
  выкинуть лишнее, чем заметить отсутствие нужного); видимость `search.expression` в ответе, чтобы промах было видно;
  reranker и golden set — следующий change.
- **[Порча запроса при переписывании] потеряно условие → уверенный ответ не про того пациента** → проверка
  `constraints` с откатом; `is_followup` и `constraints_lost` в ответе как наблюдаемый сигнал.
- **[Двойная латентность] два сетевых круга к LLM на реплику** → переписывание на быстрой модели, таймауты раздельные;
  стриминг не вводим, пока ответ не проверен целиком.
- **[Beta `json_schema`] на части моделей запрос отклоняется** → дефолт `function_calling`, переключение переменной после
  проверки.
- **[LangChain-зависимость] `langchain-gigachat` тянет `langchain-core`; для LangChain 1.0+ у них отдельный пакет** →
  версия фиксируется при добавлении, слой изолирован в `clients/llm.py`, откат на SDK `gigachat` не затрагивает сервисы.
- **[Нет оценки качества] без golden set регресс retrieval невидим** → первый шаг после запуска — 10–15 ручных вопросов по
  загруженному клинреку; метрики и эталоны — отдельный change.
- **[Freemium-лимиты] GigaChat-3-Ultra доступна физлицам в freemium; лимит токенов общий с экспериментами** → ретраи
  ограничены, `usage.total_tokens` доступен из `include_raw` для учёта.
- **[Разметка от модели] markdown может быть некорректным или содержать внешние ссылки** → рендерим безопасно:
  HTML не выполняется, внешние адреса показываются текстом, битая разметка выводится как текст.
- **[Лента в памяти] разговор не переживает перезагрузку страницы** → это требование, а не дефект: после F5 чат
  начинается заново, медицинский текст не остаётся на диске.

## Migration Plan

Изменение аддитивное: новый роутер, новый экран, новые переменные окружения с дефолтами. Существующие эндпоинты,
экраны и спеки не меняются. Откат — убрать роутер из `main.py` и маршрут со экрана; индекс Qdrant и манифесты
клинреков не затрагиваются. `openapi.json` и `schema.d.ts` перегенерируются в том же изменении.

## Open Questions

- Порог `CHAT_MIN_SCORE`: значение подбирается после первых наблюдений за оценками на реальном клинреке.
- Нужен ли поиск сразу по двум запросам (переписанный + исходный) с объединением по оценке — решается, когда станет
  видна частота потери условий по `constraints_lost`.
