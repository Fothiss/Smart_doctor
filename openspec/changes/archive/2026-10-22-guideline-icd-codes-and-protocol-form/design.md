# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что ограничивает реализацию.

- Клинрек живёт на файловой системе: `storage/guidelines/<id>/original.pdf` + `meta.json`.
  Манифест пишется атомарно (временный файл + `os.replace`) с повторами на краткую блокировку
  Windows (`app/services/guidelines.py`).
- Чанки лежат в Qdrant, payload — сериализованный `Chunk` целиком. `ChunkVectorStore.delete_guideline`
  уже умеет удалять по `guideline_id`, но вызывается ровно в одном месте — перед переиндексацией.
- `GuidelineService` не знает про векторное хранилище; про него знают `Runtime` и
  `GuidelineIndexer`. Открытие Qdrant ленивое: библиотека обязана работать, даже когда хранилище
  недоступно.
- Признак «идёт индексация» живёт в памяти процесса: `GuidelineIndexer.is_running(id)`.
- Типы фронтенда генерируются из `openapi.json` (`npm run gen:api`), поэтому схемы FastAPI — это и
  есть контракт.
- Хранилище сейчас пустое (клинреки и векторы удалены вручную), значит новый формат манифеста не
  требует миграции существующих данных.

## Goals / Non-Goals

**Goals:**

- Коды МКБ-10 у клинрека: приём при загрузке, хранение в манифесте, показ и фильтрация в библиотеке.
- Удаление клинрека как одна операция: PDF, манифест и чанки исчезают вместе, сирот в Qdrant не
  остаётся.
- Экран формы протокола с выбором готового клинрека и серверная валидация черновика, включая
  раскладку формы на атомарные пункты для будущей проверки.

**Non-Goals:**

- Справочник МКБ и автоматическая подстановка названий диагноза по коду.
- Правка метаданных клинрека (`PUT`): исправление кодов делается удалением и повторной загрузкой.
- Сохранение протоколов, идентификаторы протоколов, retrieval, вызовы LLM, вердикты, отчёты,
  PostgreSQL.

## Decisions

### 1. Коды МКБ — список, а не одно поле

Один клинрек покрывает диапазон кодов (КР62 «Гипертензия» — I10–I15), поэтому `icd_codes: list[str]`
в `Guideline`. Диапазоны (`I10–I15`) не вводим: это второй синтаксис, который придётся разбирать на
границах; вместо него — явное перечисление кодов.

Схема терпима к отсутствию поля (`default_factory=list`), потому что иначе старый манифест без кодов
перестанет валидироваться и клинрек молча пропадёт из библиотеки — `_iter_manifests` трактует
`ValidationError` как битый манифест. Обязательность живёт на входе API, а не в модели хранения.

Нормализация (обрезка, верхний регистр, удаление повторов с сохранением порядка) и проверка формата
`^[A-Z]\d{2}(\.\d{1,2})?$` — в `field_validator` схемы, а не в роутере и не в сервисе: правило одно
для загрузки, фильтра и будущих правок.

**Альтернативы:** одно поле `icd_code` — не описывает КР62; справочник с поиском — отложен, чтобы не
тащить в изменение статический датасет и автокомплит.

### 2. Сопоставление кода при фильтрации — префиксное на границе сегмента

`app/services/icd.py`, чистая функция без FastAPI:

```
stored == query  or  stored.startswith(query + ".")  or  query.startswith(stored + ".")
```

Так `I10` находит клинрек с кодом `I10.1`, `I10.1` находит клинрек с `I10`, а `I1` не находит
`I10`. Регулярка «начинается с» здесь не годится: она дала бы ложные совпадения на 3-значных
рубриках.

Фильтр применяется в `GuidelineService.list` вместе с фильтром по статусу — сервис и так обходит все
манифесты, отдельный индекс не нужен на текущих объёмах.

**Альтернатива:** хранить в Qdrant payload и искать средствами векторного хранилища — избыточно,
коды нужны и до индексации (`uploaded`, `failed`).

### 3. Удаление: сначала векторы, потом файлы

Порядок важен: если упадёт Qdrant, клинрек остаётся целым и библиотека не расходится с хранилищем.
Обратный порядок дал бы ровно тех сирот, от которых избавляемся: манифеста нет, векторы есть, и
цитата резолвится в документ, которого больше нет.

Оркестрация — в `Runtime.delete_guideline(guideline_id)`:

1. `indexer.is_running(id)` → `409` (тот же признак, что использует `POST /index`);
2. `store.delete_guideline(id)` — синхронно в рабочем потоке; `VectorStoreError` → `503`, файлы целы;
3. `GuidelineService.delete(id)` — `shutil.rmtree` каталога, `FileNotFoundError` → `404`.

Почему в `Runtime`, а не в `GuidelineService`: сервис намеренно не знает про векторное хранилище, и
это разделение уже держит индексация. Пробрасывать стор в сервис значило бы открывать Qdrant на
каждый запрос библиотеки.

`GuidelineService.delete` остаётся честным файловым удалением и проверяется отдельным тестом.

**Альтернатива:** soft delete (пометка `deleted_at`) — не нужен: отчётов ещё нет, а половина кода
библиотеки начала бы фильтровать флаг.

### 4. Протокол: валидация без сохранения, эндпоинт отдельно от `POST /api/protocols`

`POST /api/protocols/validate`. `POST /api/protocols` в [`API.md`](../../../backend/API.md) уже
задуман как создание протокола с идентификатором; занимать этот путь валидацией без сохранения
значило бы поменять его семантику в следующем изменении.

Схемы (`app/schemas/protocol.py`):

```
IcdDiagnosis        code, name
ProtocolPrescription kind: Literal["drug","procedure"], name, dose?, frequency?, duration?
ProtocolForm        complaints, diagnosis, diagnosis_description?, prescriptions
ProtocolDraftRequest   guideline_id, guideline_version?, form
ProtocolDraftResponse  guideline (ref), form, statements[]
```

Правила: для `procedure` дозировка, кратность и длительность запрещены (`model_validator`) — иначе
сервер молча принимает бессмысленные данные; пустой `prescriptions` допустим.

Лимиты на длины (жалобы, название, описание) — в схеме, чтобы один запрос не приносил произвольный
объём текста.

**Альтернатива:** валидировать только на клиенте — тогда контракт формы не попадёт в `openapi.json`,
и следующему изменению (проверке) пришлось бы вводить схему заново.

### 5. Атомарные пункты строит сервер

`statements: list[str]` в ответе валидации, чистая функция `build_statements(form)`. Формат строк —
тот же, что ждёт `Verdict.item` в будущем отчёте:

```
Жалобы: <текст>
Диагноз: I10 — Гипертензия
Описание диагноза: <текст>
Назначение: Амлодипин, 5 мг, 1 раз в сутки, постоянно
Процедура: ЭКГ
```

Пустое необязательное поле пункта не даёт. Строки, а не структура — потому что `Verdict.item` в
контракте отчёта строка.

Почему сервер, а не клиент: пункты — вход будущего retrieval, и одинаковый парсер нужен и при
валидации, и при проверке. Дублировать его на клиенте значит получить два разных набора пунктов.

### 6. Экран формы — новый маршрут, состояние в React

`/protocol/new`, ссылка из шапки рядом с библиотекой. Состояние формы — обычный `useState`, без
`localStorage`: спека явно говорит, что после перезагрузки форма пуста, и сохранять черновик в
браузере значило бы обещать персистентность, которой нет.

Выбор клинрека: `GET /api/guidelines?status=ready`, список в `select`. Если код МКБ диагноза
валиден, клиент сортирует уже полученный список так, чтобы совпадающие коды шли первыми
(`sortByIcdMatch`, чистая функция с тестом) — жёсткая фильтрация не годится: при несовпадении врач
увидел бы пустой список.

Кнопка «Проверить» отправляет черновик на валидацию и показывает результат: сведения о клинреке,
подтверждённую форму и список пунктов, которые уйдут в проверку. Никакого «проверка пройдена» —
соответствие клинреку в этом изменении не считается.

**Альтернатива:** сохранять черновик в `localStorage` — противоречит выбранному «валидация без
хранения».

### 7. Поле МКБ при загрузке — одно текстовое поле с перечислением

Форма загрузки уже плотная; список кодов вводится строкой «I10, I15», разбивается на клиенте и
уходит повторяющимся form-полем `icd_codes`. FastAPI принимает `list[str]` из `Form`. Отдельный
компонент-«чипсы» отложен вместе со справочником.

## Risks / Trade-offs

- [Опечатки в кодах без справочника] → проверка формата и нормализация; справочник — следующее
  изменение. Уже сейчас кривой код можно исправить только удалением и повторной загрузкой.
- [Удаление рвёт связи, когда появятся отчёты] → сейчас отчётов нет; при их появлении `DELETE`
  должен начать отклоняться (`409`), если у клинрека есть проверки. Точка расширения — `Runtime.delete_guideline`.
- [Флаг «индексация идёт» живёт в памяти процесса] → гонка «удалить во время старта индексации»
  возможна при нескольких процессах uvicorn; в single-user MVP процесс один. В худшем случае
  индексатор получит отсутствующий каталог и запишет отказ в лог.
- [Удаление теперь зависит от Qdrant] → при недоступном хранилище удаление отвечает `503`, а
  библиотека продолжает работать: стор открывается лениво и только в момент удаления.
- [Протокол не сохраняется] → потеря формы при перезагрузке — осознанное ограничение, зафиксировано
  в `protocol-form`.
- [**BREAKING** для загрузки] → `icd_codes` обязателен в `POST /api/guidelines`; единственный
  клиент — наш фронтенд, обновляется вместе с бэкендом.

## Migration Plan

1. Бэкенд и фронтенд деплоятся вместе: новый формат формы загрузки несовместим со старым.
2. `openapi.json` регенерируется, `npm run gen:api` обновляет `src/api/schema.d.ts`.
3. Миграция данных не нужна: хранилище пустое. Если у кого-то остались манифесты без `icd_codes`,
   они читаются с пустым списком и показываются как клинреки без кодов.
4. Откат — обычный откат коммита; удаление клинреков необратимо, но и восстанавливать нечего.
