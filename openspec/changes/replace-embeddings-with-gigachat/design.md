# Design

## Context

Смотивировано в `proposal.md`. Ниже — только состояние и ограничения, которые формируют подход.

Текущий шов для эмбеддингов уже существует и менять его не нужно:

```
    services/indexing.py  -> embedder.encode_documents(batch)   (внутри asyncio.to_thread)
    services/retrieval.py -> embedder.encode_query(text)        (внутри asyncio.to_thread)
                                      |
                                      v
                    Embedder Protocol (dimension, model_id, encode_*)
                                      |
                            SentenceTransformerEmbedder (удаляется)
```

Ограничения, проверенные на живом API и в исходниках `gigachat` 0.2.3:

| Факт | Значение / следствие |
|---|---|
| `EmbeddingsGigaR` на scope `GIGACHAT_API_PERS` | доступна, ответ `200` |
| Размерность | 2560 |
| Контекст | 4096 токенов; 1500 символов чанка ≈ 570 токенов, 7-кратный запас |
| `usage.prompt_tokens` | есть в каждом элементе `data` |
| `index` | приходит, порядок совпадает с `input` |
| Пустая строка в `input` | принимается, `prompt_tokens: 2`, вектор возвращается молча |
| Батч 256 текстов | принимается |
| Латентность | 71 мс/чанк при батче 8, 30 мс при 32, 6 мс на коротких при 256 |
| Токенов на чанк 800 символов | ~303 (2.65 символа на токен) |
| `GigaChat.embeddings()` | уже обёрнут `@_with_auth` (кэш и продление токена) и `@_with_retry` (429/5xx/TransportError, уважает `Retry-After`) |
| Модель в запросе | передаётся при вызове, а не при создании клиента |
| `Embedding` в ответе | требует `usage`, `index`, `object`, `embedding` |
| Разбор ответа | `model_class(**response.json())` — при несоответствии летит `pydantic.ValidationError`, а не `GigaChatException` |

Ещё два ограничения проекта: `distance=COSINE` в Qdrant (нормализация векторов не нужна) и
`CHAT_MIN_SCORE=0` (порог по умолчанию выключен, потому что масштаб оценок старой модели не измерялся).

## Goals / Non-Goals

**Goals:**

- Заменить провайдера эмбеддингов, не меняя сервисы `indexing.py`, `retrieval.py`, `chat.py`.
- Сделать отказ внешнего сервиса эмбеддингов наблюдаемым и отличимым от отказа хранилища и модели.
- Сделать стоимость индексации измеряемой без обращения к кабинету провайдера.
- Убрать PyTorch из образа.

**Non-Goals:**

- Настройка `CHAT_TOP_K` и `CHAT_MIN_SCORE` под новую шкалу оценок — это отдельная работа после снятия
  метрик GigaChat.
- Переразметка golden set и перевыпуск отчётов Qwen.
- Поддержка двух провайдеров эмбеддингов одновременно (переключатель не делаем — решение о полной
  замене принято).
- Кэширование или дедупликация векторов по тексту: повторная индексация платит заново.
- Пересборка батчей при частичном отказе провайдера (весь батч повторяется целиком).

## Decisions

### D1. Клиент — SDK `gigachat`, а не `langchain-gigachat` и не свой HTTP

`GigaChat(...).embeddings(texts, model=...)` берём напрямую. Обоснование: пакет уже в зависимостях,
внутри него уже реализованы кэш access token с продлением за 60 с до истечения (`threading.RLock` —
безопасно из рабочих потоков) и повторы с экспоненциальным backoff и учётом `Retry-After`.

Альтернативы: `langchain_gigachat.embeddings.GigaChatEmbeddings` — тонкая обёртка над тем же вызовом,
добавляет неиспользуемые `embed_query`/провайдеры и собственный префикс запроса, который пришлось бы
выключать; свой `httpx`-клиент — пришлось бы писать OAuth, продление токена, повторы и маппинг ошибок,
то есть повторять уже готовый код.

### D2. Синхронный вызов, существующие `asyncio.to_thread` переиспользуются

`Embedder` остаётся синхронным. Оба места вызова уже уходят в рабочий поток, поэтому замена провайдера
не трогает сервисы вообще. Асинхронный `Protocol` потребовал бы переписать `_index_blocking` в
async-цепочку (чанкинг и разбор PDF блокирующие), добавить `await` в двух сервисах и обновить фейки в
тестах — цена без выигрыша для однопользовательского MVP.

### D3. Один экземпляр клиента на процесс, без `with`, без закрытия

`with GigaChat(...)` из примера документации нужен только ради `close()` в конце блока. Клиент
создаётся лениво при первом обращении и живёт до конца процесса: соединения и access token кэшируются
внутри него. В `Runtime.close()` его не закрываем — как и клиент чата, у которого метода закрытия нет;
единственный ресурс, который действительно надо отпускать, — локальный Qdrant.

### D4. Креденшелы и транспорт — общий базовый класс `GigaChatSettings`

Новый `app/config/gigachat.py` объявляет `token`, `scope`, `base_url`, `verify_ssl_certs`,
`ca_bundle_file`, `timeout`, `max_retries` с теми же алиасами (`GIGACHAT_*`). `LLMSettings` и
`EmbeddingSettings` наследуются от него: поля остаются плоскими, `settings.llm.gigachat_token`
продолжает работать, `llm.py` не меняется.

Альтернативы: дублировать поля в `EmbeddingSettings` — токен и `verify_ssl_certs` объявлены дважды и
могут разъехаться; передавать `LLMSettings` в клиент эмбеддингов — домен эмбеддингов начинает зависеть
от настроек чата, против разделения доменов в проекте.

Следствие, которое нужно учесть заранее: `tests/test_settings.py` сейчас требует, чтобы алиасы были
уникальны **по всем доменам сразу** (`test_env_aliases_are_unique_and_upper_snake`). После наследования
`GIGACHAT_TOKEN`, `GIGACHAT_SCOPE` и остальные видны и в `LLMSettings`, и в `EmbeddingSettings` через
`model_fields`, поэтому тест упадёт. Инвариант уточняется по смыслу: уникальность проверяется внутри
домена, а повтор алиаса между доменами допускается только тогда, когда оба класса наследуют его из
общего `GigaChatSettings`. Ослаблять проверку до «просто сними уникальность» нельзя — она ловит как раз
случай, когда одну переменную объявили дважды независимо.

### D5. Ответ сверяется по `index`, `model` и размерности

Векторы раскладываются по `item.index`, а не по порядку списка: перепутанный вектор молча привязал бы
чужой текст к чанку. `response.model` сверяется с настроенной моделью — метаданные клинрека не должны
врать о том, кто посчитал векторы. Длина каждого вектора сверяется с настроенной размерностью до записи
в хранилище, чтобы ошибка называла причину, а не приходила из Qdrant невнятным отказом.

### D6. Инструкция запроса — шаблон с `{text}` в одном параметре

`EMBEDDING_QUERY_TEMPLATE` (по умолчанию русский вариант из рекомендаций Sber для retrieval-задач,
адаптированный под домен) заменяет пару `EMBEDDING_QUERY_INSTRUCTION` + жёсткую сборку
`"Instruct: ...\nQuery:"`. Документы кодируются без инструкции — как и раньше. Шаблон обязан содержать
`{text}`, иначе настройки падают при сборке: иначе подстановка потеряется молча.

### D7. Учёт токенов — через возвращаемое значение, а не через состояние клиента

`encode_documents` возвращает `EmbeddingResult(vectors, tokens)`: сервис индексации складывает токены
по батчам и пишет итог в журнал один раз на клинрек. Курсор `usage` на самом клиенте не годится: клиент
один на процесс, и параллельный поиск запроса из чата подмешал бы свои токены в сумму по клинреку.
Мутабельный счётчик на клиенте — та же проблема. Точечное изменение сервиса (одна строка на батч) —
наименьшая цена за честный учёт.

Сумма пишется в журнал и при отказе: накопленное до падения число токенов уже оплачено, и скрывать его
означало бы терять стоимость упавших прогонов. Счётчик растёт только после успешного ответа на батч,
поэтому повтор упавшего батча в сумму не попадёт дважды.

### D8. Таксономия ошибок эмбеддера

`EmbeddingError` остаётся базой; добавляется `EmbeddingAuthError` для отклонённого ключа. Маппинг:
`AuthenticationError`/`ForbiddenError` → `EmbeddingAuthError`; `RateLimitError` (после исчерпания
повторов), `ServerError`, `httpx.TransportError`, `TimeoutError` → `EmbeddingError`; `BadRequestError`/
`UnprocessableEntityError` → `EmbeddingError` с причиной; `pydantic.ValidationError` → `EmbeddingError`
«неожиданный формат ответа». В чате `EmbeddingError` отображается в `502` с причиной, называющей сервис
эмбеддингов, рядом с `LLMError`; сейчас он не перехвачен и уходил бы общим `500`.

Уточнение по живому вызову: неверный ключ GigaChat отклоняет как `400` **от OAuth-сервера**, а не как
`401`. По коду ответа отказ в доступе неотличим от ошибки в теле запроса, поэтому класс ошибки
определяется по адресу, с которого пришёл отказ (`/oauth` в URL) — иначе неверный ключ выглядел бы
как «сервис отверг запрос», что уводит от причины.

### D9. Пустой текст — отказ, а не пропуск

Пустая или пробельная строка не отправляется провайдеру: бросается `EmbeddingError` с позицией в батче
и без текста. Пропускать такой фрагмент нельзя — чанк молча выпал бы из поиска, а инвариант требует
ссылки на конкретный фрагмент. Чанкинг (`CHUNK_MIN_CHARS=300`) пустых чанков не создаёт, поэтому
срабатывание проверки означает ошибку, которую нужно исправлять, а не скрывать.

### D10. Батч 32 по умолчанию

`EMBEDDING_BATCH_SIZE=32`: 30 мс/чанк против 71 мс при 8. Прежнее значение 8 было привязано к памяти
GPU, у API такого ограничения нет; 256 тоже принимается, но крупный батч увеличивает цену повтора при
отказе.

### D11. Чистка настроек и зависимостей

Удаляются `EMBEDDING_DEVICE`, `EMBEDDING_THREADS`, `EMBEDDING_MAX_SEQ_LENGTH`, `EMBEDDING_MODEL_PATH`,
`ML_MODELS_DIR` и соответствующие поля; `EMBEDDING_MODEL` → `EmbeddingsGigaR`, `EMBEDDING_DIM` → 2560.
Из `pyproject.toml` уходят `torch`, `sentence-transformers` и оба pytorch-индекса вместе с
`[tool.uv.sources]`; `Dockerfile` не меняется по структуре, но перестаёт тянуть CUDA-колёса.

### D12. Eval не переписывается

В `eval/run.py` меняются только создание эмбеддера (две строки) и импорт — через фабрику
`build_embedder(settings)` по образцу `build_llm_client`. Схема отчёта, `summarize`/`compare`, промпты
не трогаются. Метрики Qwen остаются в `reports/{a,a2,b3}.json`; новые прогоны пишутся под другими
именами (`a4`, `a5`, `b6`), сравнение — через `--baseline`.

От модели `chunk_id` действительно не зависит, но зависит от `guideline_id`, а он меняется при
загрузке того же PDF заново. Поэтому после смены модели пришлось один раз перепривязать разметку:
`chunk_dump.json` пересобран по текущему индексу, в `cases.toml` заменены `guideline_id` и 21
ожидаемый `chunk_id`. Совпадение текстов и позиций проверено (427 из 427), отчёты Qwen не тронуты.

## Risks / Trade-offs

- **Индексация больше не работает офлайн.** Падение провайдера или сети останавливает индексацию →
  клинрек уходит в `failed` с причиной, называющей сервис эмбеддингов, и доступен для повтора вручную.
  Автоматической доиндексации в этом изменении нет.
- **Платный внешний вызов, ~10 ₽ за клинрек на 220 страниц** (2500 чанков × ~303 токена × 14 ₽/1M) →
  число израсходованных токенов пишется в журнал, стоимость видна по факту.
- **Лимиты и 429 у scope `PERS`.** SDK повторяет запросы с учётом `Retry-After` → `max_retries`
  берётся из общих настроек; при исчерпании повторов индексация падает с явной причиной, а не зависает.
- **Повторы блокируют рабочий поток.** `time.sleep` в SDK — до 60 с на попытку, `max_retries=3` даёт
  худший случай около трёх минут внутри индексации → HTTP-сервер не страдает (индексация в отдельном
  потоке), но клинрек дольше остаётся в `processing`. Это принимается ради простоты.
- **Нарушение совместимости пространства векторов.** Старая коллекция `guideline_chunks__1024` и новый
  вектор 2560 не смешиваются: размерность входит в имя коллекции, а клиент сверяет длину вектора до
  записи. Если забыть поменять `EMBEDDING_DIM`, индексация упадёт с явной причиной, а не запишет мусор.
- **Хранилище вырастает в 2.5 раза** (2560 × 4 байта против 1024) → для однопользовательского MVP
  приемлемо; пересмотр не нужен.
- **Два OAuth-хендшейка** (чат и эмбеддинги) → не вредно: один запрос раз в ~30 минут на клиент.
- **Метрики несравнимы напрямую между моделями.** Отчёт пишется под новым именем, а `--baseline`
  сравнивает только изменившиеся кейсы, не смешивая шкалы оценок.
- **Golden set привязан к `guideline_id`, а не только к тексту.** Проверено на практике: перезагрузка
  того же PDF даёт новый `guideline_id`, а `chunk_id` считается как
  `uuid5(namespace, f"{guideline_id}|{version}|{position}|{digest}")`, поэтому все ожидаемые
  идентификаторы в наборе перестают существовать и `L2` падает в ноль при исправном поиске. Лечится
  перепривязкой разметки: `chunk_dump.py` по текущему индексу плюс замена идентификаторов; тексты и
  позиции при неизменном PDF и чанкинге совпадают один в один (проверено: 427 из 427).
- **Свежий отчёт `eval` покажет регрессию поиска** без изменения ретривера — новая шкала оценок и другое
  пространство векторов; поэтому настройка `CHAT_MIN_SCORE` вынесена из этого изменения.

## Migration Plan

Порядок важен: локальный Qdrant держит каталог заблокированным, а веса модели больше не нужны.

1. Остановить бэкенд (локальный режим Qdrant освободит каталог).
2. Удалить `backend/ml_models/` и каталог локального хранилища `backend/storage/qdrant` — оба
   владелец удаляет сам, ни один из них не пересоздаётся кодом.
3. `uv sync` (пересоберёт окружение без PyTorch), пересобрать образ бэкенда.
4. Обновить `.env`: `EMBEDDING_MODEL=EmbeddingsGigaR`, `EMBEDDING_DIM=2560`,
   `EMBEDDING_BATCH_SIZE=32`, `EMBEDDING_QUERY_TEMPLATE=...`; удалить `EMBEDDING_DEVICE`,
   `EMBEDDING_THREADS`, `EMBEDDING_MAX_SEQ_LENGTH`, `EMBEDDING_MODEL_PATH`, `ML_MODELS_DIR`.
   `GIGACHAT_TOKEN` остаётся тем же.
5. Запустить бэкенд, проверить `/health` и что коллекция `guideline_chunks__2560` создана.
6. Переиндексировать клинреки по одному: `POST /api/guidelines/{guideline_id}/index`; после каждого
   прогона сверить число израсходованных токенов в журнале.
7. Снять метрики: `python eval/run.py --name gigachat --baseline b3`; старые отчёты не перезаписывать.

Откат: вернуть предыдущую версию кода, снова положить веса в `ml_models/` и вернуть старые значения
`EMBEDDING_*`. Векторы при откате придётся считать заново — старая коллекция удалена на шаге 2. Для
однопользовательского MVP с единственной библиотекой клинреков это приемлемо.
