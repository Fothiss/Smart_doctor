# guideline-library Specification

## Purpose

Даёт врачу библиотеку загруженных клинических рекомендаций: загрузку PDF, обзор списка с состоянием
каждого документа и понятные отказы, когда файл не принят.

## Requirements

### Requirement: Список клинреков

Интерфейс SHALL показывать все загруженные клинреки, свежие загрузки первыми, с названием, именем
исходного файла, размером, датой загрузки и текущим статусом обработки.

#### Scenario: Открытие библиотеки с загруженными клинреками

- **WHEN** пользователь открывает экран библиотеки, и в хранилище есть клинреки
- **THEN** отображается список, отсортированный от свежих загрузок к старым
- **AND** каждый элемент показывает название, размер, дату загрузки и статус

#### Scenario: Библиотека без клинреков

- **WHEN** пользователь открывает экран библиотеки, и в хранилище нет ни одного клинрека
- **THEN** отображается сообщение о пустой библиотеке и предложение загрузить PDF
- **AND** пустой список не показывается как ошибка

### Requirement: Фильтр по статусу

Интерфейс SHALL позволять ограничить список одним статусом обработки и MUST показывать, какой фильтр
применён сейчас.

#### Scenario: Применение фильтра

- **WHEN** пользователь выбирает статус в фильтре
- **THEN** список содержит только клинреки с этим статусом
- **AND** выбранный фильтр виден в интерфейсе

#### Scenario: Сброс фильтра

- **WHEN** пользователь сбрасывает фильтр
- **THEN** список снова содержит клинреки всех статусов

### Requirement: Постраничная догрузка списка

Интерфейс SHALL загружать список страницами и MUST NOT показывать один и тот же клинрек дважды после
догрузки.

#### Scenario: Догрузка следующей страницы

- **WHEN** пользователь запрашивает следующую страницу, и сервер вернул её полностью
- **THEN** новые клинреки добавляются в конец существующего списка
- **AND** управление догрузкой остаётся доступным

#### Scenario: Список исчерпан

- **WHEN** сервер вернул страницу короче запрошенного размера
- **THEN** управление догрузкой больше не предлагается как доступное

### Requirement: Загрузка PDF клинрека

Интерфейс SHALL принимать PDF-файл, необязательное название клинрека и обязательный список кодов
МКБ-10, отправлять их на сервер и после успеха MUST показывать созданный клинрек в списке.

#### Scenario: Успешная загрузка

- **WHEN** пользователь выбирает PDF-файл, указывает хотя бы один код МКБ и подтверждает загрузку
- **THEN** клинрек создаётся на сервере со статусом `uploaded`
- **AND** созданный клинрек появляется в списке библиотеки вместе со своими кодами МКБ

#### Scenario: Название не указано

- **WHEN** пользователь загружает PDF, не заполнив название
- **THEN** клинреком становится имя файла без расширения
- **AND** коды МКБ сохраняются как указаны

#### Scenario: Выбор файла

- **WHEN** пользователь выбирает файл в диалоге или перетаскивает его в область загрузки
- **THEN** выбранный файл и его размер видны до подтверждения загрузки
- **AND** загрузка не начинается без подтверждения

#### Scenario: Коды МКБ не указаны

- **WHEN** пользователь не указал ни одного кода МКБ
- **THEN** отправка недоступна, а поле кодов помечено как обязательное
- **AND** запрос на сервер не отправляется

#### Scenario: Несколько кодов МКБ

- **WHEN** пользователь указывает несколько кодов МКБ, например `I10` и `I15`
- **THEN** все коды сохраняются у клинрека

### Requirement: Ход загрузки

Интерфейс SHALL показывать ход передачи файла и MUST блокировать повторную отправку того же файла,
пока передача не завершилась.

#### Scenario: Передача идёт

- **WHEN** загрузка файла началась и ещё не завершилась
- **THEN** интерфейс показывает прогресс передачи
- **AND** повторный запуск загрузки недоступен

#### Scenario: Передача завершена

- **WHEN** сервер ответил на запрос загрузки
- **THEN** индикатор прогресса исчезает

### Requirement: Отказ при неподходящем файле

Интерфейс SHALL показывать причину отказа, когда сервер отклонил файл как пустой, не PDF или
превышающий допустимый размер, и MUST сохранять уже выбранный файл доступным для замены.

#### Scenario: Файл не является PDF

- **WHEN** сервер отвечает `400` на загрузку
- **THEN** интерфейс показывает текст причины отказа
- **AND** список библиотеки не меняется

#### Scenario: Файл превышает лимит размера

- **WHEN** сервер отвечает `413` на загрузку
- **THEN** интерфейс показывает, что файл превышает допустимый размер

### Requirement: Отказ при дубликате

Интерфейс SHALL при ответе `409` сообщать, что PDF с таким содержимым уже загружен, и MUST давать
переход к этому существующему клинреку.

#### Scenario: Повторная загрузка того же PDF

- **WHEN** сервер отвечает `409` и передаёт идентификатор уже загруженного клинрека
- **THEN** интерфейс сообщает о дубликате и показывает ссылку на существующий клинрек
- **AND** переход по ссылке открывает этот клинрек

### Requirement: Состояния экрана библиотеки

Интерфейс SHALL различать загрузку данных, пустой результат и ошибку получения списка.

#### Scenario: Список загружается

- **WHEN** запрос списка ещё не завершился
- **THEN** интерфейс показывает индикатор загрузки

#### Scenario: Ошибка получения списка

- **WHEN** запрос списка завершился ошибкой
- **THEN** интерфейс показывает сообщение об ошибке и способ повторить запрос
- **AND** пустой список при этом не показывается

### Requirement: Достоверность статуса обработки

Интерфейс SHALL показывать статус клинрека ровно таким, каким его вернул сервер, и MUST NOT помечать
клинрек как готовый к проверке или как обрабатываемый, пока сервер не сообщил такой статус.

#### Scenario: Клинрек только загружен

- **WHEN** статус клинрека — `uploaded`
- **THEN** интерфейс показывает его как загруженный, а не как готовый к проверке

#### Scenario: Обработка завершилась ошибкой

- **WHEN** статус клинрека — `failed` и сервер передал причину
- **THEN** интерфейс показывает признак ошибки и её причину

### Requirement: Текст ошибки API для пользователя

Интерфейс SHALL извлекать читаемое сообщение из ответа сервера независимо от того, передан `detail`
строкой или объектом, и MUST NOT показывать пользователю необработанное представление объекта.

#### Scenario: Ошибка со строковым detail

- **WHEN** сервер отвечает ошибкой, где `detail` — строка
- **THEN** интерфейс показывает эту строку

#### Scenario: Ошибка с объектным detail

- **WHEN** сервер отвечает ошибкой, где `detail` — объект
- **THEN** интерфейс показывает содержательное сообщение, а не сериализованный объект

### Requirement: Обновление статуса без действий пользователя

Интерфейс SHALL отражать смену статуса клинрека без перезагрузки страницы и MUST прекращать обновление,
когда статус стал окончательным (`ready` или `failed`).

#### Scenario: Статус меняется сам

- **WHEN** клинрек загружен и индексация идёт
- **THEN** интерфейс показывает смену статуса без действий пользователя
- **AND** страницу не нужно перезагружать, чтобы увидеть новый статус

#### Scenario: Окончательный статус

- **WHEN** статус клинрека стал `ready` или `failed`
- **THEN** интерфейс прекращает обновлять его состояние

### Requirement: Признак хода индексации

Интерфейс SHALL показывать, что обработка идёт и насколько она продвинулась, пока статус клинрека —
`processing`.

#### Scenario: Прогресс виден

- **WHEN** статус клинрека `processing` и сервер сообщает число обработанных чанков
- **THEN** в строке клинрека видно, что обработка идёт
- **AND** видно, насколько она продвинулась

### Requirement: Повтор индексации из интерфейса

Интерфейс SHALL предлагать повторить индексацию для клинрека в статусе `failed` и MUST NOT предлагать
повтор, пока индексация идёт.

#### Scenario: Повтор после отказа

- **WHEN** статус клинрека `failed`
- **THEN** в строке клинрека доступно действие повтора индексации
- **AND** после повтора клинрек снова становится обрабатываемым

#### Scenario: Повтор во время обработки недоступен

- **WHEN** статус клинрека `processing`
- **THEN** действие повтора недоступно

### Requirement: Признак векторизации

Интерфейс SHALL показывать, что клинрек векторизован, вместе с числом чанков и идентификатором модели, и
MUST NOT показывать этот признак для статусов `uploaded`, `processing` и `failed`.

#### Scenario: Клинрек готов

- **WHEN** статус клинрека `ready`
- **THEN** отображается признак того, что документ векторизован
- **AND** видны число чанков и модель эмбеддингов

#### Scenario: Клинрек не готов

- **WHEN** статус клинрека `uploaded`, `processing` или `failed`
- **THEN** признак векторизации не отображается

### Requirement: Обязательный код МКБ при загрузке клинрека на сервере

Сервер SHALL требовать хотя бы один код МКБ-10 при создании клинрека, MUST отклонять код вне формата
«заглавная латинская буква, две цифры, необязательная точка и одна-две цифры» и MUST сохранять коды
нормализованными: без пробелов по краям, в верхнем регистре и без повторов.

#### Scenario: Коды переданы

- **WHEN** загрузка содержит `i10` и `I10.1 `
- **THEN** клинрек получает коды `I10` и `I10.1`
- **AND** коды видны в метаданных клинрека

#### Scenario: Коды не переданы

- **WHEN** запрос на загрузку не содержит ни одного кода МКБ
- **THEN** сервер отвечает `400` и указывает на отсутствующие коды
- **AND** клинрек не создаётся

#### Scenario: Код вне формата

- **WHEN** среди кодов есть `10` или `гипертензия`
- **THEN** сервер отвечает `400` и указывает отклонённый код

#### Scenario: Повтор одного кода

- **WHEN** среди кодов дважды указан `I10`
- **THEN** клинрек получает один код `I10`

### Requirement: Коды МКБ в строке клинрека

Интерфейс SHALL показывать коды МКБ каждого клинрека в списке библиотеки и MUST NOT домысливать
названия диагнозов по коду, пока справочника МКБ нет.

#### Scenario: Клинрек с кодами

- **WHEN** у клинрека сохранены коды `I10` и `I15`
- **THEN** обе коды видны в строке клинрека

#### Scenario: Коды не указаны

- **WHEN** у клинрека нет сохранённых кодов
- **THEN** строка клинрека показывает, что коды не указаны
- **AND** клинрек не скрывается из списка

### Requirement: Фильтр библиотеки по коду МКБ

Интерфейс SHALL позволять ограничить список клинреков кодом МКБ и MUST комбинировать этот фильтр с
фильтром по статусу. Сопоставление SHALL учитывать уточнение кода: код клинрека `I10` совпадает с
фильтром `I10` и `I10.1`, а код `I10` не совпадает с фильтром `I1`.

#### Scenario: Фильтр по коду

- **WHEN** пользователь вводит код `I10`
- **THEN** список содержит клинреки, у которых есть код `I10` или уточнение вида `I10.x`
- **AND** клинреки без этого кода в список не попадают

#### Scenario: Фильтр по уточнённому коду

- **WHEN** пользователь вводит код `I10.1`, а у клинрека сохранён только `I10`
- **THEN** этот клинрек попадает в список

#### Scenario: Ничего не найдено

- **WHEN** по введённому коду нет ни одного клинрека
- **THEN** интерфейс сообщает, что под фильтр не подходит ни один клинрек
- **AND** пустой результат не показывается как ошибка

#### Scenario: Сброс фильтра по коду

- **WHEN** пользователь сбрасывает фильтр по коду
- **THEN** в списке снова видны клинреки с любыми кодами, кроме отсечённых фильтром по статусу

### Requirement: Удаление клинрека из библиотеки

Интерфейс SHALL предлагать удаление клинрека из списка и MUST требовать подтверждение перед
отправкой запроса на сервер. После успешного удаления клинрек MUST исчезнуть из списка без
перезагрузки страницы.

#### Scenario: Подтверждение удаления

- **WHEN** пользователь нажимает удаление у клинрека
- **THEN** интерфейс просит подтвердить удаление
- **AND** до подтверждения запрос на сервер не отправляется

#### Scenario: Отказ от удаления

- **WHEN** пользователь отменяет подтверждение
- **THEN** клинрек остаётся в списке, а данные не меняются

#### Scenario: Удаление выполнено

- **WHEN** сервер подтвердил удаление
- **THEN** клинрек исчезает из списка библиотеки
- **AND** открыть его оригинал по прежней ссылке больше нельзя

#### Scenario: Удаление не удалось

- **WHEN** сервер отказал в удалении
- **THEN** интерфейс показывает причину отказа
- **AND** клинрек остаётся в списке

### Requirement: Удаление клинрека на сервере

Сервер SHALL удалять клинрек полностью: оригинальный PDF, метаданные и все чанки клинрека в
векторном хранилище. Удалённый клинрек MUST NOT оставаться источником цитаты. Сервер MUST отклонять
удаление, пока по клинреку идёт индексация.

#### Scenario: Клинрек удалён

- **WHEN** сервер получил запрос на удаление существующего клинрека, по которому не идёт индексация
- **THEN** метаданные и PDF клинрека удалены
- **AND** запрос фрагмента, принадлежавшего этому клинреку, отвечает `404`

#### Scenario: Повторное удаление

- **WHEN** запрос на удаление пришёл для клинрека, которого нет
- **THEN** сервер отвечает `404`

#### Scenario: Удаление во время индексации

- **WHEN** по клинреку идёт индексация
- **THEN** сервер отвечает `409` и не удаляет ни файлы, ни чанки

#### Scenario: Векторное хранилище недоступно

- **WHEN** удаление чанков невозможно из-за недоступного векторного хранилища
- **THEN** сервер отвечает `503` и не удаляет метаданные и PDF
- **AND** клинрек остаётся в библиотеке
