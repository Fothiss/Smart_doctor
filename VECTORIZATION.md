
## Что такое Runtime

`app/runtime.py` — один объект на процесс, который держит всё дорогое:

```python
Runtime(settings, embedder=None, store=None)
  .guidelines  -> GuidelineService       (манифесты и PDF на диске)
  .embedder    -> Embedder               (модель; грузится при первом обращении)
  .store       -> ChunkVectorStore       (Qdrant; открывается перед первой записью)
  .indexer     -> GuidelineIndexer       (один рабочий слот индексации)
  .start()     -> снимает зависшие индексации при старте
  .close()     -> закрывает векторное хранилище
```

Зачем он нужен:

- **Модель нельзя создавать на запрос.** Веса ~1.2 ГБ, загрузка десятки секунд, память процесса.
- **Локальный Qdrant держит эксклюзивную блокировку каталога** — второй клиент в том же процессе
  получит ошибку, а не второе подключение.
- **Всё это должно быть необязательным.** Загрузка, список и просмотр PDF работают и тогда, когда
  модели в `ml_models` ещё нет: поэтому `embedder` и `store` создаются лениво, а падение индексации
  заканчивается статусом `failed`, а не отказом сервера.

Как это подключено:

```
create_app(settings, runtime=None)
    runtime = runtime or Runtime(settings)     <- можно подменить в тестах
    app.state.runtime = runtime
    lifespan: runtime.start() ... runtime.close()

роутеры: Depends(get_runtime) -> Runtime -> нужный клиент
```

`app/routers/dependencies.py` — провайдеры зависимостей: `get_runtime` берёт рантайм из состояния
приложения, `get_guideline_service` отдаёт роутерам сервис клинреков из рантайма. Раньше этот
провайдер собирал сервис из настроек на каждый запрос — теперь собирать нечего, клиенты уже живут.

## Контракт: что изменилось

| Эндпоинт | Изменение |
|---|---|
| `POST /api/guidelines` | по-прежнему `201` и `status: uploaded`, но сразу после ответа стартует индексация |
| `POST /api/guidelines/{id}/index` | **новый**: `202` + `processing`; `409` если индексация уже идёт; `404` если клинрека нет |
| `GET /api/chunks/{chunk_id}` | **новый**: реализован вместо плана |
| `GET /api/guidelines/{id}` | те же поля плюс `chunks_total`, `chunks_indexed`, `embedding_model`, `indexed_at` |

**Ломающее изменение:** у `Chunk` вместо одного `bbox` теперь список `rects: [{page, bbox}]` —
13 % чанков лежат на двух и более страницах, одним прямоугольником их не подсветить. Поля `page` и
`bbox` остались и равны первому прямоугольнику, поэтому старый код вьювера продолжает работать.

## Надёжность

- **Атомарный манифест.** `meta.json` пишется во временный файл и подменяется через `os.replace`:
  статус обновляется многократно во время индексации, а список библиотеки читает тот же файл.
  Запись и чтение повторяются при отказе в доступе: на Windows подмена файла и чтение во время неё
  могут кратко конфликтовать (плюс OneDrive и антивирус), а без повтора клинрек мигал бы в списке.
  Проверено замером: 200 перезаписей под непрерывным чтением — 0 ошибок записи, 0 промахов чтения.
- **`ready` только после записи.** Статус меняется на `ready` после того, как все чанки записаны;
  прерывание даёт `failed`, а не «почти готово».
- **Один рабочий слот.** Вторая индексация того же клинрека отклоняется, а не конкурирует за CPU/GPU.
- **Разбор PDF и инференс — в рабочем потоке** (`asyncio.to_thread`), цикл событий не блокируется,
  API продолжает отвечать во время индексации.
- **Реконсиляция при старте.** Клинреки, застигнутые в `processing`, переводятся в
  `failed("индексация прервана перезапуском сервера")` — иначе они зависают навсегда.
- **Детерминированные `chunk_id`.** UUIDv5 от клинрека, версии, позиции и хеша текста: повторная
  индексация не осиротит ссылки в ранее выданных отчётах.

## Замеры, на которых стоят решения

- **Индексация 220-страничного клинрека:** 427 чанков, ~460 токенов каждый.
  На CPU (4 из 8 ядер) — ~25 минут; на GTX 1650 — **2.4 минуты** (341 мс на чанк против 3.5 с).
  Отсюда `EMBEDDING_DEVICE=auto` и CUDA-сборка PyTorch как источник зависимости; CPU-индекс
  (`pytorch-cpu`) объявлен в `pyproject.toml` для будущего контейнерного образа.
- **Извлечение текста:** 433 298 символов, 7151 строка, 33–52 с на документ.
- **Чанкинг:** чанк = 1..N абзацев одной секции; 13 % чанков попадают на две страницы и больше,
  поэтому подсветка описывается списком прямоугольников.
- **Локальный Qdrant** выбран потому, что контейнеры в этой итерации не поднимаются: тот же код
  переключается на сервер одной переменной `QDRANT_MODE`.

## Что не менялось

`docker-compose.yml`, `backend/Dockerfile`, `frontend/nginx.conf`, PostgreSQL — контейнерный путь
остаётся отдельной итерацией (там же нужно вернуть CPU-сборку PyTorch в образ и смонтировать
`ml_models` томом).
